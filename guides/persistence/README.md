# TS3W.exe PC 1.67 — game saves and object persistence

This dossier preserves PC 1.67 `TS3W.exe` save/load evidence without requiring Ghidra. It contains 64 native registration records with original executable byte exports and disassemblies, 13 captured Ghidra pseudocode exports, Ghidra xrefs, four unique local managed-type decompilations plus links to shared type exports, original string bytes, and a direct-call graph. The local and linked C# files are decompiler exports from retail `ScriptCore.dll` in `scripts.package`.

## Writer and reader contract visible in pristine managed code

[PersistWriter.End](managed/ScriptCore_PersistWriter.cs) writes version `1280`, signature `1397375567` (`0x534a424f`), class/object counts and offsets, a resource-key table, then object data. [PersistReader.Load](managed/ScriptCore_PersistReader.cs) rejects versions `>=1536`; for versions `>=512`, it checks that exact signature; for `>=1280`, it seeks to and reads the resource-key table before the class and object tables. These are corresponding original writer/reader paths, rather than an assumed file format from one side. `LoadSaveManager`'s `BeginLoadObjects` creates `NativePersistReader` and `PersistReader`, loads through `FastStreamReader`, and captures `TaskStateCollection`; `EndLoadObjects` runs post-load hooks and disposes the reader/state. Its `BeginSaveObjects` creates `NativePersistWriter`, `PersistWriter` and a `TaskStateCollection`; `EndSaveObjects` writes via `FastStreamWriter` and disposes them. The complete methods, including null/error branches, are in the managed export.

## Native DBPF and failures

The [save dispatcher `0x00aaf6c0`](native/pseudocode/00aaf6c0.c.txt) constructs a `World/LoadSaveManager/DBPF` object, uses a write mode, calls `0x00aaa810`, and has early return values visible as `1`, `2`, `0xf`, `0x10`, `0x11` in pseudocode. The [DBPF write helper](native/pseudocode/00aaa810.c.txt) has stage-specific return values `9` through `0xd` and a zero success path. The [load dispatcher `0x00aafb40`](native/pseudocode/00aafb40.c.txt) also constructs that DBPF object and reads through it. Original [native byte exports](native/bytes/00aaf6c0.bin), [save disassembly](../../evidence/native/functions/00AAF6C0_LoadSaveManager_DispatchSave.asm) ([annotated pseudocode](../../evidence/native/functions/00AAF6C0_LoadSaveManager_DispatchSave.c)) and [load disassembly](../../evidence/native/functions/00AAFB40_LoadSaveManager_DispatchLoad.asm) ([annotated pseudocode](../../evidence/native/functions/00AAFB40_LoadSaveManager_DispatchLoad.c)) are present for checking each branch. The exact meaning of each numeric error is unresolved; those numbers are observed return values, not assigned error names. Static string evidence includes `World/LoadSaveManager/DBPF`, `%s.bad%d` and `.bad`; Ghidra [xref readback](native/save-failure-string-xrefs.json) places `.bad` at `0x00aafa2c` inside the save dispatcher. This establishes that a `.bad` path is built; the final filesystem effect still needs tracing of the called file helper or a runtime test.

## How to inspect and what remains open

- [registered-boundaries.json](registered-boundaries.json) contains 64 relevant registration rows, each with the exact 8-byte native table record, managed signature and marshaling metadata, and paths to `.bin`/`.asm.txt` exports. All rows reached the next saved Ghidra entry before the 2,048-byte cap. That bound is an export boundary, not proof of complete control flow.
- Eleven disassembly spans and eleven original byte spans shared with loading point to byte-identical canonical copies in [the loading dossier](../loading/README.md). The catalog and direct-call graph give the exact relative paths.
- [internal-boundaries.json](internal-boundaries.json) indexes five key unregistered helpers. [direct-call-graph.json](direct-call-graph.json) records direct x86 `CALL rel32` edges in the exported spans; virtual/indirect calls are absent. [native/ghidra-decompiler-exports.json](native/ghidra-decompiler-exports.json) indexes the pseudocode and its warnings. [native/ghidra-xrefs.json](native/ghidra-xrefs.json) records function/data xrefs; [native/string-witnesses.json](native/string-witnesses.json) has original null-terminated string bytes.
- [ScriptCore.TaskControl.cs](../../evidence/managed/types/ScriptCore.TaskControl.cs) preserves managed yield-object save/load declarations; the native table entries are in the 64-row catalog. [ScriptCore.GameUtils.cs](../../evidence/managed/types/ScriptCore.GameUtils.cs) supplies save-file deletion/rename/copy managed callers; its matching native wrappers are exported here.

This is static evidence only; it does not establish a successful save, normal quit, and fresh-process reload. The exact callback dispatch from native into `BeginLoadObjects` / `BeginSaveObjects`, complete indirect DBPF call targets, error-code meanings, ownership at every native allocation, and `.bad` handling remain unresolved. The canonical save-wrapper body at `0x00742c40` has been recovered to its original final `RET`; older bounded captures retain their original limitations. Ghidra may still mislabel other calling conventions across indirect host calls. Use the original byte exports and pristine managed declarations when those conflict with pseudocode.
