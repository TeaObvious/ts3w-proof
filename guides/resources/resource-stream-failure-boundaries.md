# Stream backing, allocator and packed-provider failure boundaries

Reserve, write, resource opening, codec expansion and release are different operations. A false low-byte result does not by itself promise untouched output, rollback or a particular managed exception. This reference describes their selected static contracts in the [Original PC1.67 input](../../evidence/reference.json); runtime success, caller validity, dynamic children and lifetime remain separate questions.

The [complete selected instruction ledger](../../evidence/native/resources/stream-failures/instruction-evidence.json) retains32 ranges/context views,31 distinct roots and5,056 unique Original bytes/1,809 starts. Two views at4EC540 overlap: their28/31-byte views are preserved, while shared bytes/starts are counted once. Historical metadata and bounded CFG contexts are explicitly distinguished; none becomes a new definition or a repaired logical extent. GNU/LLVM Original verification and the existing independently checked stream/DBPF contracts are reused.

The [address/source index](../../indexes/resource-stream-failures.tsv) and [selected data/imports](../../evidence/native/resources/stream-failures/data-and-imports.json) connect the fields, table slots, allocator prefix and declared import targets below. The [three genuine current C projections](../../evidence/native/resources/stream-failures/current-c-projections.json) have been scientifically reconciled, with their type/return/whole-variable limits preserved. They are not maintained canonical ASM/C pairs; this reference adds zero such pairs.

Current canonical pairs are resolved in the linked address/source index. Immutable links labeled source retain the reviewed historical projections. Canonical availability does not close the body, annotation, ABI or lifetime limits below.

## Concrete fields and distinct state

Offsets below are hexadecimal and relative to their stated object. A field role is a bounded reader/writer relationship, not a complete source-language class layout.

| Object | Offset | Selected role |
| --- | --- | --- |
| MemoryStream | +4 | Backing-record pointer, replaced by reserve after old-backing release. |
| MemoryStream | +8 | Allocation-label input forwarded to backing/payload allocation; separate from the allocator pointer. |
| MemoryStream | +10 / +14 / +18 | Logical length / capacity / position. Reserve changes only capacity; the writer can update length/position under its own policy. |
| MemoryStream | +1C | Growth-permission byte checked by callers; reserve itself does not enforce it. |
| Backing record | +4 / +8 | Allocator / payload pointer. The backing-record allocation prefix and payload are separate release targets. |
| Backing record | +C / +10 | Signed reference-count comparison / payload-release flag byte. Final release is not an atomic or general lifetime validation. |
| Packed provider | +14 / +1C | Selected open/access state, cleared by the bounded cleanup path. |
| Packed provider | +260 / +264 / +268 | Stream reference / borrowed buffer word / borrowed size word. The direct buffer setter does not copy or retain an owner. |
| Packed provider | +390 | Manager pointer installed/cleared by the selected callback; not a decoder-ID array. |
| Manager interface | +B8 / +D8 | Decoder-pointer slots / corresponding low16 ID words; construction initializes eight while add scans seven. |

A raw AL result, copied count, logical position and managed error code are different values. The sections below explain their exact ordering and failure boundaries.

## What the managed stream API establishes

The [fifteen selected original methods/declarations and six registration-name joins](../../evidence/managed/resources/stream-failures/selected-methods.json) are reused from the original ScriptCore S3SA input. Each complete IL selection has an annotated C# projection; the [original input identity](../../evidence/managed/reference-inputs.json) is central. Six selections are PInvoke declarations rather than CIL bodies. No target assembly was executed or newly extracted for this reference. Their `Sims3Common` P/Invokes and SafeArray/BStr metadata do not establish the native instruction ABI or host-view lifetime.

The reader constructor adopts a supplied nonzero handle only when no input array is supplied; an array selects CreateFromBuffer instead. A zero handle otherwise selects Create. The writer similarly adopts a nonzero handle or creates one. Each selected Dispose closes a nonzero stored handle and then writes zero to that managed field. This proves those ordered calls and local invalidation, not that every other borrower is invalid or that a native allocation was physically released.

The independently checked stream-transfer evidence establishes CreateFromBuffer obtains a host array view, creates/resizes native backing, copies its actual count, disables later growth, publishes a handle and drops its local reference. It does not wrap the original array storage as the stream backing. The host+70 view's pinning, lifetime, aliasing and GC protocol remain open. ReadByteArray and WriteByteArray use actual host-returned pointer/count words; their decompiler pointer and stack projections are not replacement evidence for those output words.

The selected Write wrapper returns -3 for false AL after virtual+38; the underlying writer can already have copied a prefix and advanced position. A growth-allocation failure is a different branch: it returns before this writer's memcpy. Read maps only native FFFFFFFF to -3; ordinary concrete EOF returns zero. `RaiseException` maps -7/-6/-5/-4/-3/-2/-1 to the selected exceptions, but that mapping does not establish an OOM cause or exception for every native failure. Other codes fall through.

## Reserve replaces backing; it does not set logical length

At `004DF1C0`, ECX is the stream record and the one physical stack word is requested capacity; the body ends in RET4 and establishes AL success/failure only. It does not check the growth-permission byte. Its callers `004DF530` and `004DF370`, reached through MemoryStream vtable `00FB6C00` slots+20/+38, apply their own permission/length/growth policy. The table and prior 1.5 growth factor/+24 increment evidence are reused and pinned.

| Case | Original behavior | Boundary |
| --- | --- | --- |
| Requested capacity nonzero | Choose old backing's allocator when nonzero, otherwise default getter `004D9C90`; allocate a 0x14-byte backing record through `004E0A20`; initialize it through `004DEF60`; retain it; reject a null data pointer. | Returned record/data are separate allocations. Neither allocator success nor a fixed allocator implementation is assumed. |
| Record/data allocation fails | Return false AL; on a constructed record with null data, call `004DEE00` first. No explicit store replaces stream+4 or capacity+14 on these exits. | Called allocation/default-getter/release routines can have other effects. This is a local field/order fact, not a global rollback, leak-freedom, or OOM guarantee. |
| Old and new backing both exist | Copy unsigned `min(requestedCapacity, oldCapacity)` through the original `memcpy` thunk `00F7F286` → IAT `00F96658`, MSVCR80!memcpy. | This count is capacity-bound, not logical-length-bound. Valid backing pointers and readable old-capacity storage remain prerequisites. |
| Replacement commits | Release/decrement old backing, then set stream+4 to the new record and +14 to the requested capacity; return AL1. | Logical length+10 and position+18 are not changed here. Release return values are ignored. |
| Requested capacity zero | Skip new allocation/copy, release old backing if present, store null backing and capacity zero, return AL1. | Length/position are still unchanged. Directly calling this helper does not preserve a general `position <= length <= capacity` invariant. |

`004E0A20` physically requests `requestedObjectSize+0x10` from allocator slot+4 with the selected extra words, stores the allocator in the allocation prefix and returns base+0x10. For the reserve call the requested object size is 0x14; do not confuse the prefix, backing record, payload capacity and logical length. `004DEF60` installs table `00FB94F4`, stores its selected allocator+4, allocates the requested payload through allocator+8, stores data+8, initializes count+C to zero and byte+10 to one, and returns its receiver even if that payload allocation returned null. Stream+8 is used as an allocation-label argument, distinct from the allocator selected through backing+4/default getter. No foreign pointer type is inferred. Its caller contains an additional null-return check; that does not create a demonstrated normal ctor-null path. `004D9C90` lazily fills global `011C8984` using `0092F9C0` if currently zero. This body has no local null-result guard or synchronization.

The [backing-leaf instruction evidence](../../evidence/native/resources/stream-failures/instruction-evidence.json) establishes the selected backing-record destructor ingress: table `00FB94F4` slot0 points to qualified context `[004DF440,004DF45F)`. It writes base table `00FB318C`, conditionally calls `004E4340(receiver)` for low-byte flag1, returns the old receiver in EAX and RET4. `004E4340` accepts a cdecl pointer, skips null, reads its allocator from pointer-0x10 and calls allocator+0C with `(pointer-0x10, 0)`. This joins the actual prefix written by `004E0A20`; it is distinct from freeing the payload pointer stored in the backing record.

The same facts identify `0092F9C0`'s concrete default branch. If `011DD180` is zero it reuses `011DD184`, or initializes static `011DD168` with table `00FB9B60`; if that adapter's +4 is zero it fills +4 from shared core pointer `011CC864`. Previously initialized/global replacement paths are retained, not assumed absent at runtime. The [adapter instruction evidence](../../evidence/native/resources/stream-failures/instruction-evidence.json) establishes table+0C → qualified 16-byte context `004E4460`: load adapter+4, forward the pointer to `004E5E70`, RET8. Thus the selected default-adapter release really can reach the same shared allocator as the formatter/Slot3 chain. It does not exclude other installed allocator tables.

That adapter's allocation slots+8/+4 are existing 70-byte `004E43B0` and 90-byte `004E4400`: both query core `004E4A40` with tag `8843221A`, select specialized `004E8830`/`004E89F0` when nonnull, otherwise core `004E6F20`/`004E6F70`, and return their result. These are concrete dependency targets, not evidence of allocator success, a decoded tag meaning, or a fully understood allocation policy.

## Backing release and the shared allocator are conditional operations

`004DEE00` uses ECX backing and plain RET. A signed count+C greater than one is decremented. Otherwise byte+10 gates an allocator+0C call with `(data+8, 0)`, followed by backing virtual slot0 with flag1; the final path sets EAX zero. It does not first decrement count in the final-release case. There is no local null-receiver validation or LOCK instruction. The identical old-backing release sequence is inlined into reserve.

The previous independently checked Slot3/formatter chains reach `004E44E0` → `004E5E70` → `004E5700`. They remain explicit source reuse. `004E5E70` conditionally brackets that call with the allocator's critical-section record. Nothing here excludes shared allocation just because a resource or formatter is the caller.

`004E5700` uses ECX allocator, one pointer word, RET4. Null skips metadata updates and returns the input zero in EAX. Nonnull input requires valid preceding chunk headers and allocator lists:

* Small chunks at or below allocator+4's threshold are linked into a size bin and marked; this does not invoke an OS free.
* Larger chunks whose header mask02 is clear can coalesce with free neighbors, update boundary/list words and invoke `004E5080` and conditionally `004E54E0` for large-region trimming.
* Header mask02 set selects the separate region path: unlink it and decrement allocator+48C/+488 accounting before calling IAT `00F9625C`, proven KERNEL32!VirtualFree, with `(allocationBase, 0, 0x8000)`. The return is not checked or rolled back by this body.

There is no single normalized success Boolean across those paths. A call is not evidence that storage became inaccessible, that every chunk reaches VirtualFree, or that all foreign aliases are dead. `004E54E0` separately checks a VirtualFree decommit call `(address, size, 0x4000)` before updating its corresponding success accounting. Its conditional lock and nested list helpers do not prove a global threading/liveness contract. Both the OS operation and the allocator's internal state have concrete preconditions; no arbitrary-pointer safety is claimed.

## Packed provider state, open/cleanup and resource consumption

`004A9290` initializes the PackedFile object through offset+390, installs primary table `00FB3610` and secondary `00FB3600`, initializes its embedded stream/monitors/index state, zeros +390 and optionally calls `004A9050` with the first argument. It returns the receiver and RET8 without propagating subcall failure as a constructor status. The historical **224 bytes** mean selected dispatch data: provider144 + index60 + codec16 + manager consumer4. They are not the provider object's allocation size.

`004A9050` rejects nonzero provider+14; otherwise clears+264/+268 and assigns the null-terminated UTF-16 name range through `00408D60` into +24. It neither opens the file nor proves that string allocation succeeded. PackedFile vtable+18 points to `004A7AB0`; the inventory has no function-range row at that exact address, so `[004A7AB0,004A7CDD)` below is a two-decoder original CFG **context**, not a newly created function.

That context uses ECX provider and three physical words/RET0C. Argument3 nonzero first stores argument1 in +18, including on later failure. With +264 nonzero it accepts only `(arg1 & 3)==1`, argument2 in {3,6}, and a successful provider virtual+78 predicate, then writes +14/+1C. In the ordinary branch it requires byte+C nonzero and +14 zero. It can reuse +2D0 under the third flag; otherwise it establishes access state, checks an existing +260 stream's slot+10 flags or assigns/configures the embedded +34 stream and calls its virtual+4C with four words. The exact host/OS stream implementation remains a dependency.


The separate [provider-input instruction evidence](../../evidence/native/resources/stream-failures/instruction-evidence.json) joins table+54/+58 to qualified contexts `[004A6F10,004A6F57)` and `[004A6F60,004A6F97)`. With provider+14 nonzero each fails before replacement. The first otherwise compares stream pointers, calls new stream+4 before storing it at+260, then calls old stream+8, and returns AL1; an identical pointer skips those calls. It does not prove retain/release success or solve aliases. The second clears the provider name range, stores its two physical words directly at+264/+268 and returns AL1. It neither copies that buffer nor retains a buffer owner in this body. This concrete non-copying path is distinct from managed CreateFromBuffer's copied MemoryStream data; external validity/size/lifetime and actual caller ownership of the supplied resource buffer remain open.

After opening it checks physical size/header/index conditions through `004A78E0`, virtual+78, virtual+80 and virtual+A0. Multiple failure branches explicitly invoke `004A7990`. Thus neither blanket atomic-open rollback nor blanket absence of cleanup is justified. The selected existing metadata body `[004A7990,004A79FD)` conditionally clears +26C, calls +260 virtual+18, nulls/releases +260 only if it equals the embedded stream address, clears +14/+1C and returns AL1. Other fields and external stream objects are not proven destroyed. `004A8820` additionally closes/clears selected record state, calls index virtual+10 and two `004AB300` operations; those callees and the provider's complete lifetime remain open.

`004A9C70` reuses the accepted index-load contract: cache index size via index+0C, establish an index object when needed, skip row parsing for zero header count, read the selected physical buffer, call index+34, optionally notify +2D4, free the temporary buffer through its allocator, and gate subsequent callbacks/state. Repeated index virtual+0C calls are preserved; a stable result is not assumed. Its old C and complete owned ASM were rechecked against original bytes, not replaced by an invented cleaner body.

`004B0760` reuses the complete 350-byte manager consumer: under its selected monitor, try cache, select provider/loader, request provider+34 `(key, &stream, access1, mode3, loadFlags1, nullRecordOut)`, then call loader+1C if successful and release a nonnull local stream via+8. These six request words and the physical ECX+six stack words/RET18 are authoritative. The retained old C projects a false return-address argument, unaff monitor receiver and shifted formals; its names/types do not establish a correct public prototype. The concrete incoming virtual caller's argument pushes remain unclosed. Dynamic cache/loader failure side effects and output ownership are not inferred from the manager's AL.
